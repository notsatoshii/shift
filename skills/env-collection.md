# Shift — secure API key collection

When the project needs external services (database, auth provider, AI models, payment), the user has to create accounts and give us API keys. This doc is the pattern for doing that safely and in plain English.

## Principles

1. **Never ask for a key until it's actually needed.** Collect just-in-time, not up front. The user won't know what `STRIPE_SECRET_KEY` means in a vacuum.
2. **Explain the service in plain English first.** What it does, why we need it, whether it costs money.
3. **Link to signup, walk the user through creating the key.** "Go to [URL]. Click 'Create API Key'. Copy the value. Paste it here."
4. **Store in `.env` (gitignored), never in `.env.example` or committed files.**
5. **Confirm receipt, never echo the key back.** "Got it — I've saved your OpenAI key." not "Your key is sk-abc123..."
6. **One key at a time.** Never batch-ask.

## Template for collecting a key

### Step 1 — Introduce the service

> To [do the thing], we need an account with **[service]** — that's [one-sentence explanation]. [Cost note: "Free to start" / "$X per million tokens" / "Free tier covers first N operations/month"].

Example:

> To send emails when users sign up, we need an account with **Resend** — that's a service that sends transactional emails from your domain. Free for the first 3,000 emails per month.

### Step 2 — Guide the signup

> Here's what to do:
>
> 1. Go to **[signup URL]**
> 2. Create an account (use your normal email)
> 3. Once you're in, find **[Settings → API Keys]** (or similar — I'll walk you through it if the UI has changed)
> 4. Click **Create API Key**. Give it a name like `shift-[project-name]`.
> 5. Copy the whole key that appears — it's a long string starting with `[prefix]`.
> 6. Paste it here.

Always tell the user what the key looks like (prefix, length) so they know they've got the right thing.

### Step 3 — Receive and store

User pastes the key. You say:

> Got it — I've saved your [service] key. You won't need to enter it again.

Write it to `<project-dir>/.env` (create if missing). Update state:

```json
"env_vars": {
  "collected": {
    "RESEND_API_KEY": "stored-in-env"
  }
}
```

**CRITICAL:** store the marker `"stored-in-env"`, NOT the key itself. State files should be safe to share (e.g. for support, for the future web UI). Raw secrets live in `.env` and nowhere else.

### Step 4 — Verify `.env` is gitignored

Before first commit:

> Just confirming — `.env` is in your `.gitignore`, so it'll never end up on GitHub. Your secrets stay on your machine.

If `.gitignore` doesn't have `.env`, add it silently and tell the user.

### Step 5 — Create or update `.env.example`

`.env.example` is safe to commit — it lists the variable names without values, so another developer (or the user on another machine) knows what they need. Format:

```
# Project: <name>
# Generated by Shift on <date>. Do not put real values here — see .env for those.

RESEND_API_KEY=        # For sending emails. Get one at https://resend.com/api-keys
DATABASE_URL=          # Postgres connection string. From your Supabase project settings.
```

|---------|-----|------|-----------|
| Supabase | Database + auth | Free tier generous | Project URL + anon key + service key |
| Vercel | Hosting | Free for hobbyists | Deploys via GitHub — no key needed for first deploy |

| GitHub | Code hosting | Free | Personal access token (PAT) — classic, with `repo` scope |

## Safety gates specific to API keys

Before using a paid API for the first time in this project:

> The first call to **[service]** will cost real money (~$[estimate]). Want me to enable it now, or should we use a **dummy key** for testing first so we can verify the flow without spending?

Most first-time founders want the dummy-key option. Respect that. When they're ready to go live, do another explicit gate.

## If the user says "I don't want to do this now"

Record the remaining key in `state.env_vars.remaining` and move on. The build can proceed — features that need the key will fail gracefully until the user comes back and provides it. Make that clear:

> Got it — skipping [service] for now. The [feature] that needs it won't work until you add the key. Run `shift next` when you've got it, or just paste it in chat anytime.
